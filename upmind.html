BrandForge · Integration Guide

Integrating BrandForge into Upmind

This is the flow-level companion to the attached OpenAPI spec (BrandForge_Provisioning_API_Swagger.html) — what to call, in what order, and how a customer actually ends up inside their BrandForge workspace.

Auth: one Bearer API key per reseller, issued from your BrandForge reseller dashboard Base path: /api/godmode/v1 Format: JSON in, JSON out — every response wraps in { success, message, data }

Overview

BrandForge is the product; Godmode is the API that provisions it. There is one API key per reseller — every request scoped to that key only ever sees and affects that reseller's own customers. There's nothing WHMCS-specific in this contract: the same endpoints already power our own WHMCS integration, and you're building against the identical surface.

The shape of the integration is simple: your platform is the source of truth for billing and orders; Godmode is the source of truth for the actual BrandForge account, its plan(s), and its workspaces. Your job is to call the right endpoint at the right lifecycle moment — order placed, order suspended, order cancelled, plan changed — and to give the customer a way back into BrandForge afterward.

Getting started

Two calls to confirm your credentials work and to see what you're selling:

GET/provision/ping

Confirms your API key is valid and the service is reachable. No side effects.

GET/provision/packages

Returns every package this reseller sells. Each one's slug is the plan_code you'll use in every provisioning call below — map one Upmind product to one plan_code.

Your product catalog

There's no bulk "sync all packages" endpoint in this API — GET /provision/packages is a read, not a push. The reseller (or your onboarding flow) creates one Upmind product per BrandForge package and stores that package's slug against it. From then on, that stored plan_code is what every provisioning call below refers to.

Provisioning an order

Three different calls, depending on what the customer already has. This is the one branch your provisioning logic needs to get right.

Brand-new customer
POST/provision/create
Creates the account and its first plan in one call. Idempotent on email within your reseller scope — calling it twice for the same email returns the existing account rather than erroring, so it's safe to retry.
Existing customer buying an additional plan
POST/provision/add_plan
Additive — their existing plan(s) stay active. Credits and workspace limits sum across every active plan. A customer can hold the same plan more than once, or several different ones at once; each purchase is its own plan record under the one account.
Existing plan upgraded/downgraded in place
POST/provision/change_package
Replaces the active plan with a new one — use this for a straight swap, not for adding a second concurrent plan. Credits/limits carry forward.
ℹ Send client_id / service_id_external / product_id with create and add_plan — your own identifiers for this customer/order/product. We store them and hand them back on every response, so your webhooks and ours stay reconciled without a lookup table on either side.

Suspend, reactivate, cancel

Two families of endpoint — whole-account and single-plan. Use the wrong one and you'll affect every plan a customer holds, not just the one order that changed.

WhenCall
Customer holds exactly one plan, or the whole account changes statePOST/provision/suspend · POST/provision/unsuspend · POST/provision/terminate
Customer holds multiple plans and only one order changedPOST/provision/suspend_plan · POST/provision/unsuspend_plan · POST/provision/terminate_plan

Fire these on the same lifecycle events you'd fire against any other provisioning module — order suspended for non-payment, order cancelled, order reactivated.

Getting the customer into BrandForge

This is the part you flagged — yes, SSO is the mechanism, and it's a single call.

1

Customer clicks something in their Upmind client area

e.g. "Manage BrandForge" / "Launch my workspace" — shown once their order is active.

2

Your backend calls POST /provision/sso with service_id

Server-to-server — never expose your API key to the browser.

3

You get back a short-lived login_url

Redirect the customer's browser to it (or open it in a new tab). They land inside BrandForge already authenticated as that account.

✓ The response carries more than the spec's summary shows — alongside login_url you also get the account's current plans, credits, and reseller branding (logo, colors) in the same call, if you want to render any of that in your own client area before the customer clicks through.

Linking billing IDs after the fact

POST/provision/link_account

For an account that already exists — set or refresh client_id / service_id_external / product_id without re-provisioning anything. Use this if those identifiers weren't available at create time, or change later (e.g. the order gets re-parented to a different Upmind product).

Checking usage & status

GET/provision/status?service_id=...

Current plan, credit balance (allocated / used / remaining / over-limit), and the customer's workspaces. Poll this if you want to surface usage inside your own client area rather than sending the customer to BrandForge to see it.

Errors

Every response is one shape:

{ "success": true, "message": "...", "data": { ... } }

Failures flip success to false and drop data for an error string. The one you'll hit most: create returns 409 if the email is already registered under a different account than the one you're operating on — everything else is 422 for a missing/invalid field.
